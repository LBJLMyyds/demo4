# MAST90107 Accessibility Data Pipeline & Map

This repository contains the MVP data foundation for the Semester 2 accessibility mapping project, plus a static
frontend that turns the resulting database into a browsable, filterable map of Melbourne. It upgrades the previous
notebook-based MAST90106 work into a reproducible pipeline and SQLite database that can support:

- `Conflict Resolution Engine`
- `Accessible Walking Network`
- model evaluation and reporting

Reference repository:

https://github.com/HangyuZhao/MAST90106-group-project-accessibility-map

The frontend's data model and filter-by-accessibility-criteria approach are inspired by
[EnAccess Maps](https://www.enaccessmaps.com), a Melbourne not-for-profit that pioneered this community-reported
accessibility review model.

## Frontend / live map

`frontend/` is a static, no-build-step web app (Leaflet + OpenStreetMap, vanilla HTML/CSS/JS) that reads small JSON
files exported from `database/accessibility.sqlite`. It ships four toggleable map layers (venues, public toilets,
tactile ground surface indicators, and venues flagged with conflicting community reports), free-text search,
category and per-feature accessibility filters, a slide-in venue detail panel with confidence scores and nearest
accessible-toilet distance, and a Data Quality page that surfaces open conflicts plus known data issues.

```bash
# regenerate frontend/data/*.json from the database
python3 export_frontend_data.py

# preview locally — do NOT open index.html directly (browsers block local fetch())
cd frontend && python3 -m http.server 8000
# then open http://localhost:8000
```

To deploy it for free on GitHub Pages, see **[DEPLOY.md](DEPLOY.md)** (step-by-step, written for teammates who
haven't deployed a site before). A GitHub Actions workflow at `.github/workflows/deploy-pages.yml` re-runs the
export script and redeploys automatically on every push to `main`, so the live map always matches whatever is
committed in `database/accessibility.sqlite`.

Run the full MVP pipeline:


- `reports/data_validation_report.md`

## Pipeline Flow

```text
raw CSV files
    -> ingest
    -> clean and standardise
    -> derive accessibility features
    -> detect conflict candidates
    -> create walking-network placeholder tables
    -> validate
    -> load SQLite database
    -> write validation report
```

The current MVP uses local raw files for reproducibility. The next ingestion improvement is to automatically download public datasets, such as public toilet data from `data.gov.au` or another official open-data endpoint, then cache and validate them before loading.

## Known Data Quality Notes

`export_frontend_data.py` logs these automatically into `frontend/data/meta.json` (and they're rendered on the
frontend's Data Quality page) rather than silently dropping or guessing at bad rows:

- **~95 places outside Victoria.** A number of rows in `places` carry coordinates in other Australian states or
  overseas (Sydney, Brisbane, Perth, Hobart, even Tokyo/Hong Kong), most likely from venue-name matching against
  the wrong Google Places result upstream in `src/pipeline/ingest.py`. These are excluded from the map view rather
  than plotted at the wrong location — worth a look next iteration.
- **~50 place names with mangled characters.** Names containing literal `?` characters, from a charset mismatch
  somewhere upstream of `data/raw/enaccess_places.csv` (affects non-ASCII names — cafés, Vietnamese/Chinese venue
  names, etc.). Shown as-is; not guessed at.

See `reports/data_validation_report.md` for the pipeline's own validation output.
